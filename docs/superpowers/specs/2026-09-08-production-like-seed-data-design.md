# AI Ops 生产化模拟数据补充设计

日期：2026-09-08

## 1. 背景与目标

当前 Docker 环境已经能够正常启动，主机、发布、告警、日志、Kubernetes、Docker、SQL 审核和事件墙等模块已有基础数据，但部分可访问页面仍因关联数据缺失而显示空状态。

本次工作的目标是补充一组结构完整、时间与状态分布合理、跨模块关系一致的生产化模拟数据，使主要可访问页面具备可浏览、可筛选和可展示的内容。模拟数据在界面和业务字段中不使用“演示”“测试”或“Mock”等标记。

## 2. 已确认的现状

通过登录后的只读 API 审计，确认以下集合为空：

| 领域 | 空集合 |
| --- | --- |
| 任务中心 | 任务资源组、任务资源 |
| 告警中心 | 接收人、接收组、通知渠道、通知规则、静默规则、通知记录、告警操作记录 |
| 可观测性 | 数据源关联、链路追踪数据源、指标数据源 |
| AIOps | 知识环境、工具调用、模型调用、待执行动作、外部任务、Runbook、复盘知识 |

主机、任务执行、任务模板、任务计划、发布、事务工单、告警、日志、日志数据源、Kubernetes 集群、Docker 主机、SQL 工单及事件墙已有数据，新增内容应与这些记录关联，而不是再创建一套互不相干的数据。

CMDB、多云、IaC 和应用市场的后端子路由当前未挂载到项目主 URL 配置。该问题属于功能路由问题，本次不通过填充数据库掩盖，也不擅自扩大为路由修复。

## 3. 实现方案

新增一个独立的 Django management command，用于增量补充生产化模拟数据。该命令与现有会先清空记录的 `seed_data` 分离，默认不删除任何现有数据。

命令应具备以下性质：

- 使用稳定业务键配合 `update_or_create` 或等价逻辑，重复执行不会持续增加重复记录。
- 在一个数据库事务中执行；出现模型校验或关联错误时整体回滚。
- 优先复用已有用户、主机、告警、发布、日志数据源和 AIOps 配置。
- 对只读历史模型使用稳定的外部 ID、请求 ID、任务 ID或可复现的组合键查找记录。
- 输出各类记录的新增、更新和最终数量摘要，不输出密码、令牌或连接凭据。
- 不修改现有 `seed_data` 的清理语义，避免影响原有部署流程。

建议命令名称为：

```text
python manage.py seed_production_data
```

## 4. 数据设计

### 4.1 统一业务场景

所有新增数据围绕以下相互关联的业务场景构建：

- 电商交易链路：网关、订单、库存、支付和会员服务。
- 数据平台链路：调度、数据同步、报表和对象存储。
- 基础设施链路：Kubernetes、Docker、数据库、缓存和消息队列。
- 典型事件：接口延迟升高、库存依赖超时、数据库连接池耗尽、发布健康检查失败、磁盘容量预警。

使用已有主机和告警作为关联对象，使任务、通知、模型分析、Runbook 和复盘记录能够串成完整事件链。

### 4.2 任务资源

补充约 5 个资源组与 18 至 25 个资源项，包括：

- 生产交易集群、生产数据平台、预发布环境、公共中间件和灾备资源组。
- 主机、数据库、HTTP 服务、Kubernetes 工作负载等不同资源类型。
- 在线、维护、异常和离线等状态组合。
- 与现有 Host 记录建立引用或业务字段对应关系。

资源树至少具有两级结构，以覆盖树形导航、分组筛选和资源统计页面。

### 4.3 告警通知闭环

补充以下关联数据：

- 8 至 12 名联系人，包含 SRE、应用运维、DBA、研发值班和安全响应角色。
- 4 至 6 个值班组，成员与业务线对应。
- 4 至 6 个通知渠道，覆盖邮件、钉钉、飞书和企业微信等类型。
- 5 至 8 条通知规则，按严重级别、环境、服务和来源进行匹配。
- 已有聚合、抑制和升级策略的补充关联，以及 2 至 4 条静默规则。
- 最近 30 天的通知记录与告警操作记录，覆盖成功、失败、跳过、已确认、已认领、升级、解决和关闭等状态。

所有通知渠道均不得包含可用的真实 webhook、访问令牌或收件地址。可能触发外发的渠道和规则默认关闭，历史记录直接作为审计数据创建，不通过真实发送流程生成。

### 4.4 可观测性

补充以下配置数据：

- 2 至 3 个指标数据源，表示生产 Prometheus、长期存储 VictoriaMetrics 和预发布监控。
- 2 个链路追踪数据源，表示 Tempo 与 Jaeger。
- 4 至 6 条日志、指标、链路和 Grafana 之间的数据源关联。
- 一份 Grafana 配置，包含常用仪表盘路径和变量映射。

端点使用 RFC 1918 私网地址或 `.internal` 虚构域名，不使用真实凭据，也不主动执行连接测试或查询。

### 4.5 AIOps 数据

补充一套覆盖管理和审计页面的数据：

- 3 个知识环境，分别对应生产、预发布和数据平台。
- 8 至 12 个历史会话及其消息，主题覆盖告警分析、发布失败、容量风险和日志排障。
- 25 至 40 条模型调用，分布成功、超时、限流和失败状态，并带有合理的 Token、耗时和费用字段。
- 30 至 50 条工具调用，覆盖主机查询、日志检索、告警检索、发布查询、知识检索和 Runbook 查询。
- 8 至 12 个待执行动作，覆盖待确认、已确认、已执行、已取消、策略拦截和执行失败。
- 6 至 10 个外部任务，覆盖已排队、运行中、成功、失败和取消。
- 6 至 8 个 Runbook，每个至少包含一个版本；主题包括 CPU 高负载、磁盘扩容、服务回滚、数据库连接池和 Pod 异常恢复。
- 8 至 12 条复盘知识，与已有告警、发布和会话形成主题关联。

模型和工具审计数据只描述历史执行结果，不实际调用模型、MCP 服务或运维动作。

### 4.6 时间与状态分布

记录时间覆盖最近 90 天：

- 约 60% 集中在最近 7 天。
- 约 30% 位于 8 至 30 天。
- 约 10% 位于 31 至 90 天。

状态分布以成功和已解决为主，同时保留少量失败、超时、处理中、已取消和被拦截记录，保证列表筛选、统计卡片和趋势图不会呈现失真的全成功状态。

时间戳使用固定偏移规则基于执行时刻生成，避免所有记录拥有相同创建时间，同时保证单次运行内事件先后顺序合理。

## 5. 数据安全边界

- 界面业务字段不标记数据为演示、测试或 Mock。
- 地址只使用私网 IP、保留地址或 `.internal` 域名。
- 密码、Token、API Key、webhook secret 和 kubeconfig 均为空、不可用或使用不可认证的占位值。
- 不向外部系统发请求，不发送通知，不执行主机命令，不连接数据库，不发起模型调用。
- 不删除或覆盖用户自行创建且业务键不同的数据。
- 对可能被运行时任务扫描的配置，保持禁用或不可连接状态。

## 6. 错误处理与兼容性

- 缺少必要的已有基础对象时，命令创建最小依赖或跳过该子模块并输出明确警告。
- 模型字段或枚举不匹配时立即失败并回滚，避免只写入半套关联数据。
- 对唯一约束使用数据库已有约束和稳定业务键，避免用显示名称之外的不稳定自增 ID 判断幂等性。
- 兼容当前 Docker Compose 中的 MySQL 数据库，不依赖本机 Python 环境。
- 不要求新增数据库迁移；若实现中发现模型无法表达所需数据，应停止并重新确认设计，而不是临时增加字段。

## 7. 验证方案

实现完成后执行以下验证：

1. 运行新增命令一次，记录各模型数量和命令输出。
2. 再运行一次，确认数量不因重复执行而增长，且无唯一约束异常。
3. 执行 `python manage.py check`。
4. 运行与任务资源、告警、可观测性和 AIOps 相关的聚焦测试。
5. 登录后请求本次涉及的列表和统计 API，确认均返回 HTTP 200 且关键集合非空。
6. 在浏览器检查任务资源、告警配置、可观测性数据源与关联、AIOps 知识和审计页面。
7. 确认容器保持健康，已有登录、主机、发布、日志、SQL 审核和事件墙数据未被清空。

## 8. 完成标准

- 当前可访问但为空的目标页面均能显示结构合理的数据。
- 新增记录能够跨模块形成可理解的生产事件链，而非互不相关的随机样本。
- 命令可重复执行且不产生重复数据。
- 不触发任何真实通知、外部连接、模型调用或运维动作。
- 不影响现有 Docker 部署及已有数据。
